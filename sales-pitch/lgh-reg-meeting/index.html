補充議題與備詢

此區不在簡報主流程，按 Q 或 Esc 關閉。
Q1為什麼不讓官網直接連 HIS？
A官網是對外 CMS，外掛與佈景漏洞是常態。若直連，任一外掛漏洞都可能升級為 HIS 資料外洩。中間層讓官網在網路層到不了 HIS，防火牆也只需一條規則。
Q2Windows Server 上跑 PHP 穩定嗎？
AIIS + PHP FastCGI 是成熟方案。選它而非容器，正是因為貴院現行 ASP 就在 IIS 上，維運習慣一致、交接阻力最小。
Q3會不會影響現行掛號系統？
A新系統為獨立主機、獨立 Oracle 帳號，可與現行 ASP 並行，舊系統不需停用。建議先在測試環境驗證，確認無誤後再切換。
Q4重號問題怎麼修？
A將「找號→更新→寫入」包成單一交易，並以 SELECT FOR UPDATE 鎖住該筆 regmlimt。我方 API 目前已是這個作法。上線前會與貴院確認對櫃檯掛號的影響，並於測試環境驗證。
Q5初診可以網路掛號嗎？
A現行系統不支援，本期亦不納入。先把複診流程完整串通、穩定上線後，再另案評估。屆時需討論如何在 HIS 建立新病歷。
Q6病患資料會存在你們那裡嗎？
A不會。一律不落地，僅即時轉發。WordPress 資料庫不儲存任何身分證號、病歷號、姓名或生日。
Q7如果 VPN 申請要跑很久？
A可先開測試環境並行：貴院提供 Oracle 測試庫與測試機先行開發；或由我方提供部署腳本與文件，貴院 IT 執行、我方遠端指導。
Q8API 規格會綁死嗎？
A不會。採標準 REST + JSON，統一回應格式，文件完整交付。貴院日後可自行接手或轉由其他廠商維護。
Q9掛號尖峰（早上七點）扛得住嗎？
AAPI 獨立於 WordPress，不需 bootstrap CMS，可單獨調校與擴充。另會加上速率限制與驗證碼，防止腳本搶號。
Q10API 會沿用原本 ASP 的存取方式嗎？
A是。資料表、欄位、寫入邏輯都比照現行 ASP，不改動 HIS 結構。差別只在改用參數化查詢與單一交易，把重號與額度漏失的風險補起來。
Q11研讀舊程式時是否有其他發現？
A有幾項可在後續技術對接時一併討論的細節（連線設定檔的副檔名、掛號截止時間的判斷邊界等）。新版皆已處理，會後可另提書面說明供貴院參考。
