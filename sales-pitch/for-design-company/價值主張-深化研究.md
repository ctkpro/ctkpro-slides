# 給設計公司的價值主張——深化研究

> 服務對象：價值主張包三條任務，以及後續投影片製作。
> 上位策略：[打法②](../../../3_works/a-既有優化/ctkpro/藍圖/2-指導方針.md)——對設計公司**賣「漂亮網站」**，不賣 DMZ。
> ⚠️ 本檔是**訪談前的假說**，不是結論。標 🔬 者為待訪談驗證項。

> **v2 修正（2026-07-28，Alfred）**：①「產能失衡」假說降級——好設計不是靠量拼出來的，且不是每家都會立刻擁抱 AI，不當主論述。②**第二層升為主打**——痛點是「做得出來、但推不上去」。③第三層改用「行銷部門 vs 內部資訊團隊」情境。④刪除舊 3.1（設計公司用 AI 的程度無法預測，不談）。

## 一、前提：設計公司用 AI 做什麼（背景，不是主論述）

### 1.1 採用分布：AI 吃下「發想到提案」，沒吃下「上線」

| 工作環節 | 採用度 | 常見工具 |
|---|---|---|
| 文案、研究、摘要 | **極高** | 通用 LLM |
| 提案簡報、moodboard | **極高** | Canva、Midjourney、Figma Make |
| 視覺生成、修圖去背 | **高**（探索用，非終稿） | Midjourney、Firefly |
| UI 起稿、互動原型 | **中高** | Figma Make、v0、Framer AI、Lovable |
| **從原型到上線** | **低——斷點在此** | — |
| 終稿級品牌主視覺 | **低** | — |

參考數據：Forrester 指 74% agency 用 genAI 做摘要、70% 做競品研究；Spark 報告創意生成使用率半年內 20%→47%。

⚠️ **這張表只當背景頁用，不要當主論述。** 原因（Alfred 修正）：
- **每家設計公司的 AI 使用程度差異極大，無法預測**，簡報上斷言「你們一定在用 X」有風險。
- **好的設計不是靠量拼出來的**，是靠更深刻的觀察與體悟。用「AI 讓你產出變多」當開場，等於預設對方在拼量，可能冒犯專業。

> 🎯 **正確的開場角度**：不談他們用 AI 用得多深，只談一個**不論用不用 AI 都成立**的事實——**設計與上線之間，有一道他們跨不過去的牆。**

## 二、⭐ 第一主打：從「還原設計稿」到「把設計真正推上線」

> 這是 v2 最重要的改寫。Alfred 的判斷：「100% 還原設計稿」已無競爭力，因為 RWD／hover／focus／disabled 這些狀態，現在 AI 寫 code 都能很快處理掉。**真正的痛點是——他們做得出來，但推不上去。**

### 2.1 先承認事實：「還原畫面」確實不再是賣點

必須誠實面對：
- 設計師用 Figma Make／Lovable／v0／Framer，**已經能自己做出各式動態與效果**。
- RWD 斷點、hover/focus/disabled 狀態，AI 產 code 處理得又快又好。
- 所以再喊「我們 100% 精準還原」，不但沒有差異化，還會顯得**不了解他們現在的能力**。

> **簡報上要主動講這句**：「我們知道，畫面你們自己做得出來，而且做得很好。」——先卸下對方防備，再帶出真正的斷點。

### 2.2 真正的斷點：做得出來 ≠ 上得去（有硬證據）

**這是整份價值主張最該押的一段。** 設計師手上的原型，離「客戶 production 環境能跑的網站」之間，隔著一整層工程工作。

**證據 A：Figma Make 的 export 根本不是 production code**

- Figma 社群回報：Make 匯出的內容**常缺少關鍵專案檔**——`package.json`、`tailwind.config.js`、`tsconfig.json`、`vite.config.ts`，導致**本地重建、修改、除錯極度困難**。
- 也有回報指出：**第二次提示修改後，專案甚至會變成無法建置**。
- 目前**沒有把 Make 內容完整回流到 Figma Design 的可編輯路徑**，只能存本機副本或下載 code。
- 業界評測共識：Make 的輸出偏向**單檔化、結構鬆散、缺測試、缺本地開發環境**，複雜商業邏輯很快撞牆。

> 💡 **簡報金句**：「Figma Make 給你的不是 production code，是**一份可以跑的原型**。這兩件事之間，隔著一個工程團隊。」

**證據 B：官方託管解決了「上線」，但不等於「企業可用」**

Framer 這類平台在自訂網域與 SSL 上很成熟（DNS 指向後自動簽發、自動續期），所以**小型形象站確實不需要我們**。誠實講出這點反而加分。

但企業客戶真正會卡的不在這裡，而在：**資料位置、SLA、企業資安審查、修改權限、change management、稽核紀錄**——這些都不是設計師在工具介面內能解決的，得進到企業合約、法務與資安審核流程。

**證據 C：搬到客戶自己的環境時，工作性質從「做畫面」變成「做整合」**

一旦客戶要求放自己的主機、或接既有系統，要做的事包括：

| 工作項 | 為什麼設計師做不到 |
|---|---|
| 把生成頁面拆成可維護元件 | 要懂架構，不能維持原生生成結構 |
| 接客戶現有 API、CMS 欄位、表單後端與驗證 | 要懂 CMS schema 與後端整合 |
| 補 SEO：title/description/OG/canonical/結構化資料/語系對應 | 要懂索引機制，AI 生成常缺 |
| 補追蹤碼與事件規格（GA/GTM/像素） | 重新生成就會失效，要有版本控管 |
| 多語系路由 | 涉及路由架構設計 |
| CI/CD、staging、review、rollback | 要懂 build pipeline，否則每次改版靠手動上傳 |
| DNS、SSL、環境變數、SSR/SPA 差異 | 純工程知識 |

> **一句話**：這些工作需要的是**工程背景**——build pipeline、DNS、SSR/SPA 差異、表單安全、CMS schema、權限與環境配置。設計師能交付的是視覺與互動原型；**能上 production 的版本，通常要有工程師接手重構與部署**。

### 2.3 那「還原設計意圖」該怎麼講？（Alfred 的第一個重點）

既然「還原畫面」不是賣點了，「設計意圖」要重新定義成**兩件 AI 與工具都交不出來的事**：

**（a）意圖的「延伸」——設計稿上沒畫、但上線後一定會遇到的情況**

設計稿是**有限張數的靜態畫面**，但真實網站是**無限狀態的動態系統**。中間的差距，AI 會自己猜，而猜的依據是訓練資料的慣例，不是你的設計意圖：

- 客戶把文案從 8 個字改成 40 個字，這個版面該怎麼撐？
- 商品只有 1 筆、或有 200 筆時，這個列表長什麼樣？
- 圖片還沒上傳、API 掛掉、搜尋沒結果時，**空狀態與錯誤狀態**該長什麼樣？
- 客戶自己進 CMS 改內容後，**設計還守得住嗎？**

> 💡 **金句**：「設計稿定義的是**理想狀態**。網站上線後，99% 的時間都不在理想狀態。**我們還原的是——當現實偏離設計稿時，你原本會怎麼決定。**」

**（b）意圖的「存續」——三年後它還是不是你設計的樣子**

這一點更狠，而且直接連到 MRR：

一個網站交付後，會經歷客戶自己改內容、加活動頁、換 banner、外掛更新、瀏覽器改版。**多數網站在上線 18 個月後，已經不是設計師交出去的那個樣子了。**

> 💡 **金句**：「你花三個月做的設計，值得撐三年，而不是三個月。**我們維護的不只是網站，是你的作品集。**」

這句話對設計公司有特殊份量——**他們的作品是要拿去比稿、拿獎、放官網的**。網站爛掉，爛的是他們的招牌。

### 2.4 這一層的定位總結

| | 設計公司自己（含用 AI 工具） | CTKPro 補的 |
|---|---|---|
| 視覺與互動原型 | ✅ 做得很好 | 不碰 |
| 簡單形象站上線 | ✅ Framer 等平台夠用 | 不搶 |
| **接客戶既有系統／CMS** | ❌ | ✅ |
| **企業資安審查與合約** | ❌ | ✅ |
| **CI/CD、staging、rollback** | ❌ | ✅ |
| **SEO/追蹤/多語系工程面** | ❌ | ✅ |
| **長期維運與設計存續** | ❌ | ✅ |

> 🎯 **本層一句話**：**「你負責讓它好看，我們負責讓它上得去、活得久。」**

## 三、第二主打：無障礙——有法規當引擎的鉤子

> 位置調整：v1 排第一，v2 移到第二。理由——第二層（推上線）是**普遍且立即**的痛，無障礙是**特定客群**的痛（政府/學校/金融/上市櫃）。但無障礙的**單價與 MRR 性質更好**，且法規逼著走，仍是強牌。

### 3.1 為什麼設計公司缺這塊

約 **2/3 的無障礙問題在設計階段就決定**——顏色對比、字級行高、focus 樣式、標題階層、表單標籤、替代文字判斷，全是設計師手上的東西。

⚠️ **這個數字要小心用**。Deque 原始脈絡是「納入設計流程後減少約 67% 的**自動化可檢出**缺陷」，不等於「67% 的問題是設計師造成的」。簡報建議講法：

> 「約三分之二的無障礙問題，可以在設計階段預防——這是 shift-left 的合理規劃基準。」

### 3.2 WebAIM Million 2026（可直接上投影片）

| 指標 | 2026 | 2025 |
|---|---:|---:|
| 首頁有至少一項可自動偵測的 WCAG failure | **95.9%** | 94.8% |
| 每首頁平均錯誤數 | **56.1** | 51.0（+10.1%） |
| 低對比文字 | **83.9%** | 79.1% |
| 圖片缺替代文字 | 53.1% | — |
| 表單欄位缺標籤 | 51.0% | — |
| 空連結 | 46.3% | — |
| 跳過標題層級 | 41.8% | 39% |
| 空按鈕 | 30.6% | — |

> 💡 **金句**：「無障礙不是在變好，是在變壞——六年來的改善趨勢在 2026 反轉了。而且**六大常見錯誤佔所有自動偵測錯誤的約 96%**：少數幾個設計系統決策，被複製了幾百萬次。」

### 3.3 法規引擎：讓客戶「非做不可」的理由

- **台灣**：現行為**「網站無障礙規範（110.07）」**（對應 WCAG 2.1）。⚠️ 舊稱**「2.0 版」已不再受理申請**——講出這個細節會顯專業。主管機關＝**數位發展部**。
  - **法定義務**：政府機關、政府附屬機關（構）、**學校**（身權法第 52-2 條）。
  - 2017 年後新設或全面改版的政府/學校網站，依立法院總預算通案決議**原則上應以 AA 設計**。
  - **金融業準強制**：銀行（36 家本國銀行＋中華郵政網銀均已取得 A 以上）、保險（官網須設金融友善服務專區、A 以上）、證券（資本額 40 億以上）。
  - **一般民營企業無全面強制**，但已有 **345 家民生服務企業**取得標章（35 家 AAA），數發部明確與 **ESG** 連結。
  - ⭐ **政府採購可把 AA＋標章寫成契約義務**（例：交通部觀光署採購條款）→ 不符可能**驗收不合格、限期改善、減價或違約**。
- **歐盟 EAA**：2025/6/28 起適用。**判斷標準是「有沒有向歐盟消費者提供服務」，不是公司設立地**。基線為 EN 301 549 + WCAG 2.1 AA。⚠️ **只拿台灣標章不能自動證明 EAA 合規**——這句本身就是賣點。
- **美國 ADA Title II**：原 2026/4/24 期限已由 DOJ 於 2026/4/20 生效的 Interim Final Rule **延後一年至 2027/4/26**。⚠️ 若簡報要提**必須用更新後日期**，且它規範的是**美國公部門**，非所有私人企業。

### 3.4 標章規格（本身就是 Todo「整理成一頁」的內容）

| 項目 | 事實 |
|---|---|
| 費用 | **申請、Freego 檢測、核發全免費**（成本在改網站，不在規費） |
| 流程 | Freego 全站檢測 → 案件登錄 → **填自我評量報告**（不能只附自動掃描結果）→ 資料審核 → **人工抽檢** |
| 時間 | 登錄後**原則上 7 個工作天內**進行軟體／人工抽檢（非保證核章） |
| 退回 | 一般退回須自退回日起 **7 日後**重送；限期改善通常 **5 個工作日**內回覆 |
| 效期 | **3 年**；滿半年後可被抽測，未限期改善得撤銷 |
| 抽測 | 年度抽測比例至少達前一年度核發數的 **5%**，含身心障礙者實際操作 |

> 🎯 **話術**：「標章免費，難的是**做到能過**，以及**三年內不被撤銷**。前者要在設計階段就介入，後者需要有人長期維護——這兩件事我們都做。」

> **商業意義**：3 年效期＋半年後可抽測＋年抽 5%＝**天然的持續合規關係，不是一次性交付**。完全對上[「能綁訂閱就綁訂閱」的收費內核](../../../3_works/a-既有優化/ctkpro/藍圖/2-指導方針.md)。

## 四、第三層：資安與責任背書——用「行銷 vs 資訊團隊」情境講

> Alfred 指定的改寫方向：不要抽象講資安，要**設定情境**——來找設計公司的往往是大公司的 Marketing 部門，但東西要落地，得過自家資訊團隊那一關。

### 4.1 核心情境：設計公司真正卡關的那道門

```
大企業行銷部門  ──委託──▶  設計公司  ──交付──▶  ❌ 卡在客戶的資訊/IT 部門
    （要品牌、要速度、要活動如期上線）              （要合規、要稽核、要有人負責）
```

**這才是設計公司真正的痛**：他們的窗口是行銷部門，講的是品牌與創意，彼此頻率相合。但案子要上線，得過**一群他們完全不熟、也講不贏的人**——資訊部門。

而且這一關**通常不是設計公司的失誤造成的**，卻會算在他們頭上：專案延宕、活動開天窗、客戶不滿意。

> 💡 **金句**：「你搞得定行銷部門的美感，但**搞不定他們資訊部門的問卷**。那份問卷，我們天天在填。」

### 4.2 資訊部門到底會問什麼（可直接做成一頁投影片）

大企業的 third-party vendor risk assessment 通常不只看單一證照，而是看**「證照＋問卷＋測試報告＋合約條款＋持續監控」的整套證據鏈**：

| 類別 | 常見要求 |
|---|---|
| 制度證明 | **ISO 27001 證書**、SOC 2 Type II 報告 |
| 資安問卷 | SIG、CAIQ 或客製化 vendor security questionnaire |
| 測試報告 | **滲透測試報告**（含修補證明、重大弱點 closure 記錄）、弱點掃描／SAST／DAST 摘要 |
| 個資 | **個資處理契約（DPA）**、資料流向圖、子處理者清單 |
| 營運 | 事件通報與 **SLA 條款**、存取控管與 **MFA 設定證明**、備份/復原/刪除機制 |

IT/資安最先看的幾點：**有沒有 ISO 27001 或 SOC 2 Type II**（制度成熟度的快速證明）、**近一年內的滲透測試與修補結果**、**委外條款是否寫清楚**（用途、保存期限、刪除義務、事件通報時限）、**資安問卷能不能完整回答**。

> 🎯 **這頁的殺傷力在於**：把這張表放上投影片，設計公司會立刻意識到**「這些我一個都答不出來」**——而 CTKPro 的 **ISO 27001（公司）＋ iPAS 資安工程師（Alfred）** 正好是這張表最前面兩格。

### 4.3 為什麼資訊部門現在比以前更嚴（可引用的數據）

**Verizon DBIR 2025：第三方涉入的資料外洩比例，從 15% 翻倍到 30%。**

這是這一節最有力的數字。它解釋了一件事：**資訊部門不是在刁難，是他們自己的風險真的變高了。** 供應鏈／外包／合作夥伴已經不是邊緣風險，而是主要風險來源之一。

（DBIR 2025 另指出約 **60%** 的 breaches 涉及 human element——流程、權限、誤設與協作問題。）

**接到 2.2 的資安證據，這條線就完整了**——資訊部門擔心的事，正在 AI 生成的網站上大量發生：

| 實證 | 數字 |
|---|---|
| Tenzai 測 5 大 vibe coding 平台生成的 15 個應用 | **69 個漏洞**，約半數 high/critical；**全部**缺 CSRF 保護、**所有工具**都引入 SSRF |
| **CVE-2025-48757**（Lovable + Supabase RLS） | 170+ 專案、303 端點外洩 email、電話、付款狀態、API key、住址 |
| Escape.tech 掃 5,600 個公開 vibe-coded 應用 | 2,000+ 漏洞、400+ 暴露 secrets、175 起 PII 外洩 |
| CMU SusVibes 研究 | **61% 功能正確，但只有 10.5% 通過安全審查** |
| Veracode 2025 | AI 生成碼在 **45%** 的任務中引入安全漏洞 |

> 💡 **金句**：「**功能正確 61%，安全過關只有 10.5%。** 你的客戶的資訊部門，看的正是那 10.5%。」

### 4.4 這一層賣給設計公司的到底是什麼

**不是資安本身——設計公司不 care 資安。賣的是「讓他們過得了那一關」：**

1. **讓案子不卡關**：資訊部門要的文件、問卷、證照，我們直接提供。
2. **讓他們在客戶面前答得出來**：「開發廠商具 ISO 27001＋iPAS 資安工程師，建置時已納入資安管理方法。」
3. **讓他們不必學這些**：這是最實際的價值——他們不想懂，也不該懂。

> 🎯 **本層一句話**：**「我們不是要你懂資安，是要你不必懂。」**

⚠️ **誠實標註**：目前查不到「多少比例企業把 ISO 27001 當供應商門檻」的可靠統計數字，**簡報上不要編**。用 DBIR 的 30% 當主數據即可，其餘講機制與清單。

## 六、投影片結構建議（v2）

```
1. 開場：我們知道，畫面你們自己做得出來
   （主動承認 AI 工具的能力，卸下防備）
   ⚠️ 不談「你們產能變多了」——好設計不是靠量拼的

2. 但有一道牆：做得出來 ≠ 上得去
   （Figma Make 缺 package.json/tsconfig → 不是 production code，是原型）

3. 牆的另一邊是什麼
   （整合表：CMS、SEO、追蹤碼、多語系、CI/CD、DNS/SSL、rollback）

4. 而且還有第二道牆：客戶的資訊部門
   （行銷部門 vs IT 部門的情境圖 + 廠商審查清單）
   （DBIR 2025：第三方涉入外洩 15%→30%，所以他們變嚴了）
   （61% 功能正確、只有 10.5% 安全）

5. 第三道牆：無障礙，而且它在變壞
   （WebAIM 2026：95.9%、56.1 個錯誤、六年趨勢反轉、六大錯誤佔 96%）
   （法規：政府/學校法定、金融準強制、採購契約 AA、EAA 跨境）

6. 我們補的三件事
   （推上線與長期存續 → 過資訊部門那關 → 無障礙合規）

7. ⭐ 我們怎麼保護你
   （不接走客戶／責任分擔／掛名方式）

8. 怎麼開始
   （挑一個現有案子做免費健檢）
```

> **關於第 8 頁**：收尾**不是報價，是低門檻試水**。兩個選項——「給我一個你手上的網站，我做一份無障礙健檢報告」（Freego 免費、成本低）或「給我一個你做好但推不上去的原型，我幫你評估上線要補什麼」（直接命中第二層痛點，**更貼近 v2 主軸，建議用這個**）。符合 [DRIB「先試水、只做初級」](../../../1_me/6-做事方法-DRIB.md) 的紀律。

## 七、誠實的缺口

1. 🔬 **「行銷部門 vs 資訊部門」情境未經驗證**——這是 v2 第三層的地基，但目前是推論。訪談要問：「你們的案子有沒有卡在客戶 IT 部門過？」
2. 🔬 **「做得出來、推不上去」的痛感強度未經驗證**——證據顯示工具確實有此限制，但**不確定設計公司是否把它當痛**（也許他們早就外包掉、不覺得是問題）。這是 v2 最該問的一題。
3. ⚠️ **無障礙／SEO／效能缺乏量化研究**（資安有）。講這三項時只能講機制與案例，**不要編數字**。
4. ⚠️ **查不到「多少比例企業把 ISO 27001 當供應商門檻」的統計**，也查不到「網站專案被 IT 擋下比例」「shadow IT 占比」。簡報不要編這類數字。
5. ⚠️ **台灣個資法 2025-2026 最新修法進展未能查證**——若簡報要提個資受託監督，需另行查證官方資料。
6. **未確認 CTKPro 實際做過幾個無障礙標章案**。第三章假設我們有此交付能力；若沒做過，這層就從「已具備」變成「要先練」，**會改變 Q3 的順序**。這題只有 Alfred 能答。
